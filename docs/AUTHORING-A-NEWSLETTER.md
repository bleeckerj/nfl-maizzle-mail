# Authoring a newsletter

How to write a newsletter issue against a decompiled template — and what to do when you want a section to look different from its default styles.

This guide is generic: it applies to any template under `templates/<name>/`, whether hand-built (like `dense-discovery`) or generated by the decompiler (like the New Yorker example). When the per-template `AUTHORING.md` generators land (Phase A), each template will get its own opinionated walkthrough; until then, this is the canonical reference.

> **Quick start.** If you just want to author an issue right now:
> 1. Copy `content/<template>-source.md` (or `content/<template>-starter.md` when Phase A lands) to `content/<your-issue>.md`
> 2. Edit the `sections:` list — reorder, duplicate, remove, add
> 3. Build: `node scripts/build-newsletter.mjs content/<your-issue>.md <campaign-name> --template=<template>`
> 4. Preview the resulting `build_production/<campaign-name>.html` in a browser
>
> The rest of this doc explains what's inside each step.

---

## Mental model

A newsletter is a YAML frontmatter document with a `sections:` list. Each section has a `type:` (e.g. `article_card_pair`, `dispatch`, `masthead_logo`) and a set of named **slots** the template knows how to render (e.g. `title`, `body_html`, `image_src`).

```yaml
---
template: my-newsletter
title: "Issue #12 — Mid-week update"
sections:
  - type: masthead_logo
    logo_src: https://...
    logo_alt: Brand Logo
  - type: article_card
    title: First story
    body_html: <p>What happened.</p>
  - type: article_card    # ← same type, used again
    title: Second story
    body_html: <p>What else.</p>
---
```

The build pipeline (`scripts/build-newsletter.mjs`) reads this file, validates it, applies design tokens from `templates/<name>/section-styles.json`, and produces the final HTML email.

Two important properties:

1. **Order matters.** Sections render in the order you list them. To reorder the email, reorder the YAML list.
2. **A type can repeat.** If your template has an `article_card` type, you can use it ten times in one issue. The template renders each instance with its own slot values.

## Anatomy of a newsletter Markdown file

### Required top-level fields

```yaml
template: <name>          # which template under templates/<name>/ to render with
title: "..."              # plain string; goes into <title> and some footer chrome
sections:                 # ordered list — your email's body
  - type: ...
    ...slots...
```

### Common optional fields

```yaml
preheader: "Short preview text shown by email clients before the subject line."
sectionStylesFile: templates/<name>/section-styles.json   # auto-set by decompiler
ogImage: https://...      # Open Graph / preview image
intro:                    # template-specific block (some templates use this)
  title: Welcome
  content: <p>...</p>
header:                   # template-specific (some templates use a structured header)
  quote: ...
  author: ...
footer:                   # template-specific
  logo: ...
  unsubscribeLink: ...
```

Which optional fields a template understands depends on the template. The decompiler emits a `newsletter.schema.json` per template — check it (or call `mcp__nfl-maizzle-mail__get_template_schema`) to see exactly what the template will accept.

## Per-section slots

Each section type has its own slot set. You can discover them three ways:

1. **Look at the source-rebuild Markdown** the decompiler generated (`content/<template>-source.md`) — it has every type filled out with real values from the source email.
2. **Read the template's schema** at `templates/<name>/newsletter.schema.json` (or via the MCP tool).
3. **Read the per-component palette** in `generated/<template>-decompilation-report.json`.

### Slot kinds the decompiler emits

The classifier tags every slot with a *kind* so authors know what to put there:

| Kind | What to put | Example |
|---|---|---|
| `text` | Plain text (HTML escaped on render) | `title: "Hello world"` |
| `rich_text` | HTML with tags allowed | `body_html: '<p>Hi <em>there</em></p>'` |
| `image_url` | An image URL | `image_src: https://...` |
| `image_alt` | Alt text | `image_alt: "Logo"` |
| `link_url` | A hyperlink URL (any: `#`, `mailto:`, `https://`...) | `cta_href: https://example.com/buy` |
| `link_label` | The visible link label | `cta_label: "Read more"` |
| `date` | A date string (free-form; the template formats) | `date: "May 24, 2026"` |
| `label` | Small uppercase eyebrow / tag text | `eyebrow: "FEATURE"` |

For hand-built templates that don't have a slot manifest, you'll need to read the component HTML to see what mustache placeholders it expects.

### Registry-backed sections

Some production sections store only a registry id in the issue. The canonical build validates the compact source shape and hydrates the render fields before section-style preprocessing.

Dense Discovery and Daily Headlines support Short Takes:

```yaml
- type: short-take
  items:
    - shortTakeId: dhl-autonomous-catapult-delivery-trials
```

Each `short-take` section requires exactly one item and one non-empty `shortTakeId`. Headline, caption, image, alt text, destination, edge metadata, and width metadata come from `nfl-editorial/src/content/shortTakes.json`. Issue-level overrides are rejected. Place multiple cards by adding multiple `short-take` sections at the required positions in `sections[]`.

The build loads the registry only when the issue contains a Short Take. Inventory resolution uses `NFL_EDITORIAL_SHORT_TAKES_PATH`, then `NFL_EDITORIAL_ROOT`, then the sibling `../nfl-editorial` repository. Records without a destination render without anchors.

A registry record's `url` (destination) may be authored two ways:

- A bare string — one HTTPS URL or a site-relative path beginning with `/`. The whole card links there, tracked with the registry id as the label and `short-take` as the category.
- A tracked-link object carrying the same analytics metadata the rest of the newsletter uses:

  ```json
  {
    "href": "https://example.com/story",
    "label": "sponsored short take",
    "category": "sponsored",
    "interests": ["robotics", "logistics"],
    "intent": "consideration"
  }
  ```

  `href` is required. `label` defaults to the registry id and `category` defaults to `short-take` when omitted; `interests` and `intent` are optional. Authors set these once on the registry record, so a Short Take carries the same destination and tracking wherever it is placed.

## Reordering, duplicating, removing sections

### Reorder
Move list items around in the `sections:` list. The rendered email follows your order.

### Duplicate
Copy a section block and edit the slots:

```yaml
  - type: article_card_pair
    left_title: "Story A"
    left_dek: "..."
    right_title: "Story B"
    right_dek: "..."
  - type: article_card_pair      # ← duplicated
    left_title: "Story C"
    left_dek: "..."
    right_title: "Story D"
    right_dek: "..."
```

### Remove
Delete the list entry. No other change needed.

### Add a section type you haven't used yet
1. Look up the type in the template's palette (`list_templates` or the schema).
2. Copy its slot list from the source-rebuild Markdown or starter.
3. Fill in your values.

## Inline style overrides (the dense-discovery pattern)

Templates ship with sensible defaults in `templates/<name>/section-styles.json`. Sometimes you want ONE instance of a section to look different — a brighter background for a sponsored slot, a callout that needs a left border, an intro with a smaller font for a specific issue.

You can override styles per-section directly in the Markdown frontmatter by nesting a `containerStyles:` and/or `contentStyles:` block on the section.

### Example: the dense-discovery intro aside

```yaml
intro:
  title: Welcome
  aside:
    content: <p>Teaser/lede text that sets up the intro content.</p>
    containerStyles:            # ← overrides for THIS aside only
      backgroundColor: '#f4f1ea'
      borderLeftWidth: 3px
      borderLeftStyle: solid
      borderLeftColor: '#d7d1c6'
      padding: 12px 14px
      borderRadius: 6px
    contentStyles:
      fontFamily: "'Ubuntu', sans-serif"
      fontSize: 18px
      lineHeight: 23px
      fontStyle: italic
      color: '#3f3f3f'
      textAlign: left
  content: <p>Introduction paragraph for the newsletter.</p>
```

### The four style buckets

| Bucket | What it styles |
|---|---|
| `containerStyles` | The outer wrapper of the section — background, padding, border, radius |
| `contentStyles` | Body text — font-family, font-size, line-height, color, text-align |
| `linkStyles` | Anchor tags inside the section — color, text-decoration |
| `headingStyles` | `<h1>`–`<h6>` inside the section — font-family, font-size, color |

Each bucket accepts CSS-style properties in camelCase (`backgroundColor`, `fontSize`, `lineHeight`, etc. — not `background-color` / `font-size`).

### How overrides merge with template defaults

1. `templates/<name>/section-styles.json` provides defaults per section type.
2. A `containerStyles:` block under a specific section in your Markdown OVERRIDES the defaults for that one instance.
3. Other instances of the same type still use the defaults.
4. You only need to specify the properties you're overriding — the rest inherit.

### Global mobile font lock

Every decompiler-generated template ships with a `globalOverrides.mobileAdjustments` block in `section-styles.json` that bumps body text to 23px on screens ≤ 599px (matching the dense-discovery readability pattern). You don't need to do anything in your Markdown to opt in — components automatically get `class="mob-text"` applied so the media query targets them.

If you want to disable or change this for a specific newsletter, edit the template's `section-styles.json` — but that change affects all issues built against that template.

## Building the email

```bash
node scripts/build-newsletter.mjs content/<your-issue>.md <campaign-name> --template=<template-name>
```

Flags:

| Flag | Effect |
|---|---|
| `--no-open` | Don't auto-open the built HTML in a browser |
| `--template=<name>` | Override the `template:` in frontmatter |
| `--output-dir=<path>` | Write the build somewhere other than `build_production/` |
| `--no-dark-mode-flatten` | Disable the default defensive dark-mode flatten layer for this build |

Output:

- `build_production/<campaign-name>.html` — the email
- `build_production/<campaign-name>.link-tracking-manifest.json` — every link with its tracking metadata (for the operator API)
- `build_production/<campaign-name>.content-slots.json` — replaceable CTA/content slots for send-time experiments

The build pipeline runs these passes automatically, in order:

1. Markdown → JSON conversion (`md_to_json.mjs`)
2. Schema validation against `templates/<name>/newsletter.schema.json`
3. Registry hydration for referenced ad blocks and Short Takes
4. Link tracking normalization and manifest preparation
5. Section-style preprocessing — injects design tokens from `section-styles.json`
6. Image and link validation
7. Maizzle build (templating, CSS inlining, HTML emit)
8. Rendered link tracking metadata injection
9. Mobile font hardening
10. Content slot manifest extraction

If any pass fails, you'll see an error explaining where.

By default, the build also injects a non-persisted dark-mode flatten policy for templates that include the scaffold. In dark-mode clients that honor `prefers-color-scheme: dark`, colored sections flatten to dark gray surfaces with off-white text and blue links. Use `--no-dark-mode-flatten` to keep a build light-only.

## Send-time content slots

Templates can expose small blocks, usually CTAs, for database-owned A/B testing in `nfl-newsletter-email-soup-to-nuts`.

Mark the outer element that may be replaced:

```html
<table role="presentation" data-content-slot="footer_cta">
  ...
</table>
```

The build scans the final HTML and writes `<output-name>.content-slots.json` beside the HTML. Each manifest row includes:

| Field | Meaning |
|---|---|
| `slotKey` | Stable key from `data-content-slot`, for example `footer_cta`. |
| `displayName` | Human-readable label derived from the key unless supplied later by the operator. |
| `kind` | `cta` when the key includes `cta`, otherwise `content`. |
| `htmlSelector` | Selector the delivery system uses to replace the block. |
| `textMarker` | Plaintext marker, for example `[[content-slot:footer_cta]]`. |

For plaintext parity, add the matching marker to any manually authored text body that goes with the campaign:

```text
[[content-slot:footer_cta]]
```

The email system owns the actual variants, assignment, and click reporting. Maizzle only declares where a replacement is allowed.

## Validation

Before building, you can validate your Markdown without going through the full build:

```bash
node scripts/lint-template.mjs content/<your-issue>.md --template=<template-name>
```

Or via MCP: `mcp__nfl-maizzle-mail__validate_newsletter_markdown`.

### What lint warnings to take seriously

| Warning pattern | Take seriously? |
|---|---|
| "Unknown section type" | Yes — fix or remove |
| "Missing required field" (slot) | Usually yes — depends on whether the template can render without it |
| "Section title is empty" / "Section has no items array" | No — these come from a legacy linter that assumes the dense-discovery convention. Decompiler-generated templates use flat slots instead. Noise. |
| Schema validation failures | Yes — the template can't render the data |
| Link tracking metadata warnings | Sometimes — they often auto-default with a fallback. Read and decide. |

## Common patterns

### A simple paragraph

If your template has an `intro_paragraph` (or similar) type with a `body_html` slot:

```yaml
  - type: intro_paragraph
    body_html: |
      <p>This week we're covering three stories — a long read about hummingbirds,
      a short note about the rain, and a poem from 1882.</p>
      <p>If you missed last week's, <a href="...">catch up here</a>.</p>
```

### An article with image, headline, and body

```yaml
  - type: feature_story
    heading_html: 'A Poem for Memorial Day'
    image_block_html: '<img src="https://..." alt="" width="588">'
    body_html: '<p><strong>Read it now →</strong></p>'
```

### Embedding raw HTML safely

Any slot whose kind is `rich_text` accepts HTML. Use:

- `'single-quoted strings'` for short HTML where you escape inner single quotes as `''` (YAML rule)
- `|` (block scalar) for long multi-line HTML

```yaml
  - type: editorial_intro
    body_html: |
      <p>The first paragraph.</p>
      <p>The second paragraph with <a href="https://example.com">a link</a>.</p>
```

### Linking out

If your template has typed link slots:

```yaml
  - type: cta_button
    cta_label: "Read the issue"
    cta_href: "https://nearfuturelaboratory.com/newsletters/2026/wxx-yxx"
```

For inline links inside body HTML, just write `<a>` tags in the rich-text slot.

## When something doesn't render right

| Symptom | Likely cause | Where to look |
|---|---|---|
| A whole section is missing | The `type:` doesn't match any template branch | Compare against `list_templates` palette |
| A slot shows as `undefined` | Slot name mismatch (e.g. `title` instead of `heading`) | Check the schema or source-rebuild example |
| HTML tags show as visible text (e.g. `<em>` rendered literally) | Slot is `text` kind but you passed HTML — use a `rich_text` slot, or check that the template emits `{{{ }}}` for that slot | The decompiler auto-handles this for `rich_text` kinds; hand-built templates need it manual |
| Mobile view overflows the viewport | `min-width` from an inline style locking the table open | The decompiler-emitted layout already handles this; for hand-built templates, ensure `@media` rule overrides `min-width: 0 !important` |
| Image renders weirdly (wrong size, cropped) | Wrong dimensions on the `<img>` element, or browser/email-client quirks | Test in Litmus or Email on Acid for cross-client preview |

See [docs/TROUBLESHOOTING.md](TROUBLESHOOTING.md) for the gnarlier issues we've already debugged.

## A worked example, end-to-end

Suppose your template is `new-yorker-sample` (decompiled earlier in this session) and you want to write a one-off issue about literary horror:

```bash
# 1. Start from the source-rebuild as a skeleton you can edit
cp content/new-yorker-sample-source.md content/2026-10-31-halloween.md
```

```yaml
# 2. Edit content/2026-10-31-halloween.md
---
template: new-yorker-sample
title: "From the Archive — A Halloween Read"
preheader: "Three terrifying stories from the archive."
sectionStylesFile: templates/new-yorker-sample/section-styles.json
sections:
  - type: masthead
    logo_src: https://cdn.theatlantic.com/.../newyorker.png
    logo_alt: The New Yorker
    logo_width: '238'
  - type: section_header
    section_title: "From the Archive"
    section_dek: "Three terrifying stories for the holiday."
  - type: editorial_intro
    body_html: |
      <p>For this Halloween, we revisit three stories from the archive that
      we still think about, years later...</p>
  - type: article_card_pair
    left_section_label: "FICTION"
    left_title: "The Lottery"
    left_dek: "Shirley Jackson, 1948."
    left_byline: "By Shirley Jackson"
    left_cta_label: "Read"
    left_cta_href: "https://..."
    left_image_src: "https://..."
    left_image_alt: ""
    left_issue_date: "June 26, 1948 Issue"
    right_section_label: "FICTION"
    right_title: "Where Are You Going, Where Have You Been?"
    right_dek: "Joyce Carol Oates."
    right_byline: "By Joyce Carol Oates"
    right_cta_label: "Read"
    right_cta_href: "https://..."
    right_image_src: "https://..."
    right_image_alt: ""
    right_issue_date: "Fall 1966 Issue"
  - type: colophon
    publication_name: "The New Yorker"
    view_in_browser_href: "https://..."
    view_in_browser_label: "View in browser"
    customer_care_href: "mailto:..."
    privacy_policy_href: "https://..."
    unsubscribe_href: "#"
    sender_address: "1 World Trade Center, New York, NY"
    copyright_line: "Copyright © 2026 Condé Nast."
---
```

```bash
# 3. Build
node scripts/build-newsletter.mjs content/2026-10-31-halloween.md halloween-2026 --template=new-yorker-sample

# Output:
#   build_production/halloween-2026.html
#   build_production/halloween-2026.link-tracking-manifest.json
```

Open the HTML in a browser to preview. Send it through your delivery pipeline when you're happy.

## When you need to change the template itself (not the issue)

If you find yourself wanting *every* issue to have a different default — say, all `article_card_pair` instances should have a `#fff7e6` background — that's a TEMPLATE-level edit, not an issue-level override. Two paths:

1. **Edit `templates/<name>/section-styles.json` directly** under the `sectionStyles.<type>.containerStyles` key.
2. **Re-decompile from a source email that has the design you want** — produces a new template under a new name. Useful when the brand visually changes.

For the cleanest version of (1), see the dense-discovery `section-styles.json` as a reference shape.
